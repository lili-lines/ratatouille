In this post we look at how the mouse knows its position in the maze.
With 3 sensors, the wheel encoders & the Inertial Measurement Unit (IMU) give two things: the robot's position $(x, y)$ and its orientation, the heading. <br>
We also test the reading and the calibration of each one on the breadboard.

⏰ Plan B, in case we have no wheel encoder: we can use an optical flow sensor PMW3901 that measures displacement. Its advantage is being more precise, but it must be mounted on a mast at ≥80 mm above the ground.


## 1. The IMU and wheel encoder sensors

- Wheels Encoders → distance each wheel travelled → position $(x, y)$
- IMU gyro → the heading which way the robot faces

Each one covers the other's weakness: <br>
. encoders drift when a wheel slips, so spin without moving <br>
. the gyro drifts slowly over time

The PMW3901 needs enough light and a minimum height (≥80 mm) to focus, and it also drifts over long distances <br>

#### 1.1 Experiment

**Goal** <br>

We can see the gyro bias: the sensor returns -2°/s between each value while the gyro is not moving.
To correct this, we calibrate the gyro value at startup, then in the loop we subtract the bias before integrating:

  ```cpp
  float gyroZ_dps = (gyroZraw / 131.0) - gyroZ_bias;
  ```
After this correction there is still a drift, but a small one: even calibrated, the gyro drifts slowly. To correct this in the v2 we can use the wheel encoder.

Checking the gyro value: <br>
init value ~ 0 <br>
turn of 90° clockwise <br>
headingDeg value = -88.87 <br>
error = |headingDeg_measured − real_angle| <br>
error = |90 − 88.87| = 1.13° <br>
error < 5° so ✅

Now let's compute the CPR, for this we turn the motor shaft by hand, exactly 10 full turns. <br>
init value -166 <br>
value after 10 turns -11677 <br>
CPR = (final value − init value) / 10 <br>
CPR ≈ 1151

So we can now compute the mm per count:
the number of mm the mouse travels in one wheel turn, circumference ≈ 100mm (Ø32mm) <br>
mm per count = 100mm / 1151 ≈ 0.087mm per pulse

```cpp
const float MM_PER_TICK = 100.0 / 1151.0;               // ≈ 0.087 mm
const long TICKS_TARGET = (long)(300.0 / MM_PER_TICK);  // 30cm → 3452 ticks
```

This converts a distance in mm into a number of pulses, which is the unit of the wheel counter. So the mouse will count up to 3452 to travel 30cm.

#### 1.2 Reading the logs

The measurement chain: [xp_odometry_b.cpp]({{ site.repo }}/algo/xp_motor_odo/xp_odometry_b.cpp) runs on the Teensy and sends the heading and the counter to the serial port, [xp_log_odometry.py]({{ site.repo }}/algo/xp_motor_odo/xp_log_odometry.py) records them in CSV, and [plot_odometry.py]({{ site.repo }}/algo/xp_motor_odo/plot_odometry.py) draws the curves. Three recordings of 60 to 90 s, with `MOTOR_SPEED` at 0, then 130, then 206.

For the gyro, the three curves stay within the thickness of the line around 0. The maximum drift is 0.48° in 65 s, so 0.007°/s, against the −2°/s read before calibration. The ±5° criterion is met. And the motor noise does not significantly disturb the heading.

For the encoder, the mouse is on a stand and the wheels turn free, so this is the rotation converted into mm and not a real travel. The slope gives the median speed over 1 s windows: <br>
PWM 130 → 94 mm/s, <br>
PWM 206 → 143 mm/s. <br>
